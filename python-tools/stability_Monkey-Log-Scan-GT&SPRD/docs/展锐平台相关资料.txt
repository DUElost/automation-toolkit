在紫光展锐（UNISOC）平台上，CP（Cellular Processor，即 MSP/Modem）或 SSP（Sensor Subsystem Processor / Smart Subsystem Processor）的手动 Trigger 方式通常由展锐专属的 SIPC (Shared Memory IPC) 架构和 MODEM Control (modem_ctl / spipe) 驱动支持。

展锐平台手动触发 CP 或 SSP Panic 主要有以下三种手段：

1. 通过 Sysfs / Proc 节点直接触发（最简便）
展锐的 modem_control 驱动在 /sys/ 或 /proc/ 下暴露了用于稳定性测试（Assertion Test）的调试节点。

A. 触发 CP (Modem/MSP) Panic
以 root 权限在终端或 adb 中直接注入 assert 命令：

Bash
# 1. 常见 Sysfs 节点路径（视 Android/Kernel 版本而定）
echo "assert" > /sys/class/modem/modem/device/crash
# 或
echo 1 > /sys/devices/platform/modem_control/modem_assert

# 2. 部分 Linux 内核/内核驱动版本支持 proc 节点
echo "assert" > /proc/modem/assert
B. 触发 SSP / WCN (无线三合一/Sensor Subsystem) Panic
展锐平台通常将 WCN (Wi-Fi/BT/FM) 和 SSP (Sensor Hub/PMU Core) 作为独立的 Subsystem 进行管理：

Bash
# 触发 WCN / SSP 子系统 Assert
echo "assert" > /sys/class/modem/wcn/device/crash
# 或
echo "assert" > /sys/devices/platform/wcn_control/wcn_assert
2. 通过 AT 指令触发 Modem Assert
如果处于 Debug 版本（如 Userdebug/Eng）且已连接 AT 端口或通过 slogmodem 交互，可以直接向 CP 发送展锐私有 AT 指令：

Bash
# 通过 adb 向 spipe / smux 模拟串口发送 AT 指令
echo -e "AT+SPASSERT\r" > /dev/spipe_lte0
# 或部分 Older/3G Modem 节点
echo -e "AT+SPASSERT\r" > /dev/ttyGS0
注：AT+SPASSERT 是展锐 CP 固件中硬编码的断言测试指令，CP 收到后会立即抛出主线程 Exception 并进入 Dump 流程。

3. 利用展锐工程调试工具 (SLogModem / Ylog / Orca)
展锐平台拥有专用的日志与调试服务组件：

slogmodem (Modem Log Engine)：
可以通过 slogmodem 提供的 Client 命令行触发 CP 复位与 Dump 保存：

Bash
# 向 slogmodem 进程发送命令触发 Modem crash 抓取
slogmodem-cli assert modem
Orca / EngineerMode (工程模式)：
在拨号盘输入 *#*#83781#*#* 进入 EngineerMode（工程模式） -> Telephony -> Modem Debug -> 点击 "Assert Modem" 或 "Trigger CP Dump" 按钮。

展锐平台特有机制提示 (Dump & Reset)
Dump 抓取模式确认：
在触发 Panic 前，需通过工程模式或 sysfs 确认系统处于 Dump 模式 还是 Direct Reset 模式：

Bash
# 查看当前 dump 模式 (0: 直接重启, 1: 停在 Dump 界面/保存 Memory Dump)
cat /sys/module/modem_control/parameters/dump_enable

# 如果需要抓取完整 CP RAMDump，请确保其置为 1
echo 1 > /sys/module/modem_control/parameters/dump_enable
日志节点验证：
CP Panic 后，日志将通过 slogmodem 自动存入 /data/ylog/ 或 /data/slog/ 目录下，包含 CP_Crash 及 modem_memory.dump 文件，可直接导入 Unisoc ChannelServer / DebugServer 工具解析。

========== FATAL.JE 最终结论（2026-08-11）==========
状态：未验证（无可用触发方法，验收以已验证 6 类 + dropbox 兜底为准）

已穷尽的触发路径：
1. am crash system_server -> 仅 SWT（watchdog），非 FATAL.JE
2. kill -SEGV system_server -> FATAL.NE（native 路径），非 FATAL.JE
3. kill -9 system_server -> 无 uniview 记录（SIGKILL 无 Java 异常路径，系统软重启）
4. am crash --fatal -> 该版本（Android 16 MyOS16）不支持该选项
5. ATTS apk（JavaExceptionActivity 未注册/按钮未绑定）-> 无 fatal 路径

剩余理论路径（Binder 恶意 Parcel 注入 system_server 触发 Java OOM/异常 -> FATAL EXCEPTION
IN SYSTEM PROCESS）：需逆向 Android 16 IActivityManager（ZTE 定制 UFwActivityManagerService）
transaction code + Parcel 格式，成本高且触发后 uniview 是否记录 FATAL.JE 不确定；
经评估暂不投入，如需触发建议向展锐索取 fatal 注入工具/工程指令。

注意：FATAL.JE.103100004 在设备上从未出现过目录（无历史数据），该类型实际触发条件
（Android fatal 异常路径）在本机型上可能极少出现。
